# 스타일리스트 선택형 채팅 모드 — 기능 단위 구현 계획 및 세션 재개 가이드

> 문서 목적: 작업 세션이 중단되거나 새 세션에서 다시 시작되더라도 현재 합의와 실제 코드 기준을 잃지 않고 다음 구현 단계에 즉시 착수하기 위한 실행 문서  
> 구현 기준 브랜치: `feature/chat-main-integration`  
> 구현 우선순위: 백엔드 구현 및 기능 확인 → 프론트 연동 → 전체 통합 확인  
> 현재 상태: 설계·코드 구조 확인 완료, 기능 구현은 아직 시작하지 않음  
> 관련 인수인계 문서: 사용자가 제공한 `stylist_chat_mode_session_handoff.md`

## 1. 다음 세션 시작 지침

새 작업 세션은 이 문서를 끝까지 읽고 다음 순서로 시작한다.

1. `git status --short`로 사용자 변경사항을 확인한다.
2. 현재 브랜치가 `feature/chat-main-integration`인지 확인한다.
3. 최근 커밋과 원격 브랜치 차이를 확인한다.
4. 이 문서의 **현재 진행 체크포인트**에서 첫 번째 미완료 항목을 찾는다.
5. 이미 완료된 작업을 다시 구현하지 않는다.
6. 코드에서 확인 가능한 사항은 사용자에게 다시 묻지 않는다.
7. DB 모델 변경 시 `db_table`, `db_table_comment`, 모든 필드의 `db_comment`를 작성한다.
8. 마이그레이션 생성 후 `sqlmigrate`로 실제 테이블명과 COMMENT 구문을 확인한다.
9. 백엔드 작동 검증이 끝나기 전에는 프론트 구현을 시작하지 않는다.
10. 사용자 승인 없이 Confluence를 수정하지 않는다.

새 세션에서는 아래 체크리스트의 첫 미완료 작업부터 착수한다. 이미 파일 변경이 존재한다면 먼저 변경 내용을 읽고 이 문서의 체크포인트와 대조한다.

## 2. 확정된 제품 정책

### 2.1 스타일리스트 구성

스타일리스트는 다음 3명으로 고정한다.

| 고정 ID | 표시명 | 핵심 관점 | 표시 순서 |
| --- | --- | --- | --- |
| `minimal` | 미니멀 | 정돈, 색상·실루엣 일관성, 반복 활용도 | 1 |
| `experimental` | 실험형 | 최근 추천과 다른 관계, 새로운 조합, 반복 회피 | 2 |
| `practical` | 실용형 | 날씨, 활동성, 편의, 관리 난이도, 실제 착용 가능성 | 3 |

- 사용자는 최소 1명, 최대 3명을 선택한다.
- 최초 활성화 시 미니멀만 선택한다.
- 이후에는 현재 채팅방 선택값을 우선하고, 없으면 회원의 마지막 선택값을 복원한다.
- 카드 표시 순서는 사용자 선택 순서와 무관하게 `minimal → experimental → practical`로 고정한다.

### 2.2 추천 모드와 응답 모드 분리

기존 추천 모드는 변경하지 않는다.

```text
recommendation_mode
→ WARDROBE_BASED / NEW_ITEM

response_mode
→ DEFAULT / STYLIST
```

- 기존 `ChatSession.mode`는 추천 데이터 출처를 결정한다.
- 새로운 `response_mode`는 기본 통합 응답인지 스타일리스트별 응답인지 결정한다.
- `ChatSession.mode`는 기존처럼 생성 후 불변이다.
- `response_mode`만 같은 채팅방에서 켜고 끌 수 있다.
- 스타일리스트 모드를 꺼도 마지막 선택값은 삭제하지 않는다.
- 모드 전환을 별도 채팅 메시지로 남기지 않고 화면 상태만 변경하는 방향을 우선 적용한다. 이 항목은 최종 확정 전이므로 프론트 컴포넌트는 변경 가능하게 분리한다.

### 2.3 결과와 실패 정책

- 선택한 스타일리스트마다 코디 1개를 제공한다.
- 스타일리스트 간 토론·반박·교차 비평은 구현하지 않는다.
- 한 스타일리스트가 실패해도 나머지 결과는 유지한다.
- 공통 컨텍스트 생성 실패 또는 모든 스타일리스트 실패일 때만 전체 실행 실패로 본다.
- 완료된 카드부터 표시하는 것은 현재 필수 조건이 아니다.
- 모바일은 기존 폴링 구조를 유지해도 된다.
- `다른 추천`은 지정한 스타일리스트만 다시 실행한다.
- 실패한 스타일리스트만 별도로 재실행할 수 있어야 한다.
- 스타일리스트 카드는 핵심 문장 1개를 우선 노출하고 상세 근거는 접힌 영역에서 제공한다.

### 2.4 개인화 신호

| 데이터 | 신호 강도 |
| --- | --- |
| 실제 착용 | 강한 선호 |
| 캘린더 등록 | 강한 선호 |
| 저장한 코디 | 약한 선호 |
| 추천 카드 `LIKE` | 약한 선호 |
| 상품 클릭 | 참고 정보 |
| 추천 카드 `DISLIKE` 및 사유 | 부정 신호 |

- 캘린더 등록은 그날 실제로 입은 옷으로 간주한다.
- 최근 추천 10회를 반복 회피 기준으로 사용한다.
- 추천됨·저장됨·좋아요·클릭·착용을 동일한 행동 신호로 취급하지 않는다.

### 2.5 실험형 정책

- 요청당 구조화된 검색 가설 2개를 생성한다.
- 기존 메인 LLM이 가설 JSON을 생성한다.
- 허용된 축과 reason code만 통과시킨다.
- LLM은 아이템 ID나 최종 코디를 생성하지 않는다.
- 가설 생성 실패 시 최근 반복 슬롯을 바꾸는 규칙 기반 fallback을 사용한다.

### 2.6 말투 LLM 정책

- 제공자 교체 기능은 사용자 UI가 아니라 서버 운영 설정이다.
- 기본 구현은 기존 OpenAI 어댑터를 재사용한다.
- 동일한 인터페이스로 Gemini 어댑터를 추가한다.
- 환경변수로 사용할 제공자를 선택한다.
- 추천 엔진이 확정한 아이템과 근거만 입력한다.
- 출력은 스타일리스트별 핵심 문장 1개로 제한한다.
- 실패하거나 사실 검증에 실패하면 규칙 기반 템플릿 문장을 사용한다.

### 2.7 이미지 생성 정책

- 추천된 모든 카드의 이미지를 자동 생성하지 않는다.
- 사용자가 선택한 카드 1개만 이미지 생성 대상으로 한다.
- 프론트에서 카드 선택 즉시 이미지 생성 API를 호출한다.
- 이미지 생성 실패가 추천 카드 실패로 이어지면 안 된다.
- 같은 코디의 기존 이미지 캐시는 재사용한다.

### 2.8 회원 범위

- 스타일리스트 선택형 모드는 MVP에서 로그인 회원만 지원한다.
- 기존 게스트 채팅 기능 자체는 유지한다.
- 게스트의 스타일리스트 선택 저장·가입 이전은 구현하지 않는다.

### 2.9 후순위 제외 기능

체형의 강점 강조 또는 가리고 싶은 신체 부위에 따른 추천은 핵심 기능 완료 후 시간 여유가 있을 때만 검토한다.

현재 구현 범위에는 다음 항목을 넣지 않는다.

- 채팅 발화에서 강조·비강조 신체 부위 추출
- 체형 연출 목표의 세션 저장
- 신체 부위별 강조·보완 추천 점수
- 관련 설명 근거 코드
- 별도 체형 목표 입력 화면

기존 추천은 사용자가 말하지 않은 신체 특성을 장점 또는 단점으로 자동 분류해서는 안 된다.

## 3. 기능 단위 구현 순서

## 3.1 스타일리스트 설정 파일과 로더 구현

### 목표

미니멀·실험형·실용형의 추천 전략과 말투 설정을 코드 또는 JSON으로 버전 관리한다.

### 구현 내용

- 스타일리스트 고정 ID, 표시명, 설명, 표시 순서를 정의한다.
- `strategy_profile`과 `voice_profile`을 분리한다.
- 설정 및 프롬프트 버전을 포함한다.
- 활성화 여부와 지원 가능한 스타일리스트 ID 목록을 제공한다.
- 잘못된 설정, 중복 ID, 잘못된 표시 순서를 서버 시작 또는 로딩 시 검증한다.
- 기존 DB `PersonaProfile`은 기본 채팅 호환성을 위해 즉시 제거하지 않는다.

### 완료 조건

- 세 스타일리스트 설정이 고정 순서로 로드된다.
- 추천 전략 설정과 말투 설정이 서로 독립적이다.
- 설정 버전을 `ChatRun` 스냅샷에서 참조할 수 있다.

## 3.2 채팅·회원·실행 상태 모델 변경

### 목표

세션 현재 상태, 회원 마지막 선택, 실행 당시 상태를 서로 분리해 저장한다.

### `ChatSession` 변경 후보

- `response_mode`: `DEFAULT` 또는 `STYLIST`
- `selected_persona_ids`: 현재 채팅방 선택 배열
- `persona_selection_updated_at`: 선택 마지막 변경 시각

기존 `mode` 불변 정책은 유지한다.

### 진행 상태

- [x] `ChatSession` 응답 모드·현재 선택 배열·선택 변경 시각 및 검증
- [x] 기존 세션의 `DEFAULT`·빈 선택 배열 마이그레이션
- [x] 회원 마지막 선택 모델과 저장·조회 서비스
- [x] `ChatRun` 응답 모드·선택 ID·설정/프롬프트 버전 스냅샷
- [x] `ChatRun` 실행 당시 개인화 데이터 기준 정보
  - 메시지 접수 트랜잭션에서 스키마 버전·접수 시각·기준일 저장
  - 프로필·옷장·추천·피드백·저장·클릭·캘린더 원천의 행 수와 마지막 변경 기준 저장
  - 카테고리별 예산은 원본 값 대신 SHA-256 설정 지문 저장
  - 원본 개인화 데이터는 복제하지 않고 기존 실행과 재시도에서 스냅샷 불변 유지
- [x] 스타일리스트별 실행 상태 모델과 초기 `PENDING` 행 생성

### 회원 마지막 선택 모델

회원과 일대일 관계인 별도 모델을 추가한다.

- 사용자 FK
- `last_selected_persona_ids`
- 생성·수정 시각

게스트 행은 생성하지 않는다.

### `ChatRun` 스냅샷 변경 후보

- 실행 당시 `response_mode`
- 실행 당시 `persona_ids`
- 스타일리스트별 버전 JSON
- 전략·프롬프트 설정 버전
- 실행 당시 개인화 데이터 기준 정보

스냅샷은 워커 시작 시점이 아니라 메시지 접수와 `ChatRun` 생성 트랜잭션에서 저장한다.

### 스타일리스트별 실행 모델

부분 실패와 개별 재실행을 위해 `ChatRunPersona` 성격의 모델을 추가한다.

- `run` FK
- 스타일리스트 ID와 버전
- 고정 표시 순서
- `PENDING/RUNNING/SUCCEEDED/FAILED`
- 추천 결과 FK 또는 연결 정보
- 지연시간
- 오류 코드와 오류 메시지
- 가설·전략 스냅샷
- 재실행 횟수

추천 결과 FK는 `RecommendationResult`를 일대다 구조로 바꾸는 3.3 작업에서 연결한다.

### 마이그레이션 주의사항

- 기존 행은 `response_mode=DEFAULT`로 안전하게 채운다.
- 새 모델에는 `Meta.db_table`과 `Meta.db_table_comment`를 작성한다.
- 모든 필드에 한글 `db_comment`를 작성한다.
- 배열 JSON은 허용 ID, 중복, 길이 검증을 애플리케이션과 DB 제약 가능한 범위에서 수행한다.
- `sqlmigrate`로 테이블명과 COMMENT를 확인한다.

### 완료 조건

- 세션 상태, 회원 선택, 실행 스냅샷을 별도로 조회할 수 있다.
- 실행 후 세션 선택을 바꿔도 과거 `ChatRun` 스냅샷은 변하지 않는다.
- 스타일리스트별 상태를 독립적으로 저장할 수 있다.

## 3.3 추천 결과 모델을 다중 스타일리스트 구조로 변경

### 목표

현재 `ChatRun`당 하나인 `RecommendationResult`를 스타일리스트별 복수 결과 구조로 확장한다.

### 구현 내용

- `RecommendationResult.run`의 일대일 관계를 일대다 관계로 변경한다.
- 다음 필드를 추가한다.
  - 응답 모드
  - 스타일리스트 ID
  - 스타일리스트 버전
  - 스타일리스트 설명 문장
  - 검증된 근거 코드
  - 전략 스냅샷
- 기본 모드는 기존처럼 결과 하나 안에 최대 3개의 `OutfitComposition`을 유지한다.
- 스타일리스트 모드는 스타일리스트별 결과 하나, 코디 하나를 저장한다.
- 기존 결과는 `DEFAULT` 및 빈 스타일리스트 ID로 마이그레이션한다.
- 실행과 스타일리스트 ID 조합에 필요한 유니크 제약을 설계한다.

### 목표 관계

```text
ChatRun
├─ DEFAULT RecommendationResult 0~1개
└─ STYLIST RecommendationResult 1~3개
   ├─ minimal / OutfitComposition 1개
   ├─ experimental / OutfitComposition 1개
   └─ practical / OutfitComposition 1개
```

### 완료 조건

- 기본 추천 저장 구조가 깨지지 않는다.
- 한 실행에 최대 3개의 스타일리스트 결과를 저장할 수 있다.
- 과거 결과의 스타일리스트와 버전을 재현할 수 있다.

### 진행 상태

- [x] `RecommendationResult.run`을 일대다 관계로 변경
- [x] 응답 모드·스타일리스트 ID/버전·설명·근거 코드·전략 스냅샷 추가
- [x] `ChatRunPersona`와 스타일리스트 결과의 일대일 실행 연결 추가
- [x] 기존 결과를 `DEFAULT` 및 빈 스타일리스트 정보로 이관

- [x] 동일 `client_message_id` 재전송 시 기존 실행·스냅샷 재사용
- [x] 스냅샷 생성 실패 시 사용자 메시지까지 롤백

### 완료 조건

- 같은 `client_message_id` 재전송이 스타일리스트 실행 행을 중복 생성하지 않는다.

## 3.6 개인화 데이터 로더 구현

### 최근 추천 10회

회원의 최근 추천 결과 10회를 조회해 다음을 구조화한다.

- 코디 구성 아이템과 주요 슬롯
- 스타일·색상·핏
- 추천 스타일리스트
- 추천 시각
- 피드백과 저장 여부
- 반복된 아이템·조합

현재 실행은 제외한다.

### 캘린더 실제 착용

`CalendarEntry`와 `CalendarWardrobeItem` 연결을 사용한다.

- 캘린더 등록을 실제 착용으로 간주한다.
- 최근 7·14·30일 착용 횟수를 파생한다.
- 마지막 착용일과 최근 반복 조합을 계산한다.
- 최근 캘린더 기록에 없는 옷장 아이템을 구분한다.
- 연결된 옷장 아이템이 없는 기록으로 착용 아이템을 추측하지 않는다.

### 행동 신호

- 실제 착용·캘린더: 강한 선호
- 저장·LIKE: 약한 선호
- 상품 클릭: 참고 신호
- DISLIKE와 사유: 부정 신호

상품 클릭은 핵심 추천 흐름을 막지 않는 별도 이벤트 모델과 API로 수집한다.

### 진행 상태

- [x] 현재 실행을 제외하고 검증 통과 카드가 있는 최근 추천 실행 10회 조회
- [x] 다중 스타일리스트 결과를 실행 단위로 묶고 고정 순서로 구조화
- [x] 구성 아이템·주요 슬롯·스타일·색상·핏·스타일리스트·추천 시각 구조화
- [x] LIKE/DISLIKE 피드백과 반복 아이템·조합·슬롯 요약
- [x] 최근 추천 카드에 회원의 저장 여부와 저장 시각 연결
- [x] 캘린더 실제 착용 통계 로더
  - 오늘을 포함한 최근 7·14·30일 캘린더 등록·연결 아이템 착용 횟수 집계
  - 아이템별 마지막 착용일과 최근 30일 반복 조합 계산
  - 현재 옷장의 최근 30일 미착용·미착용 이력 아이템 구분
  - 연결 없는 캘린더는 등록 신호만 보존하고 착용 아이템은 추측하지 않음
- [x] 사용자 행동 신호 통합 서비스
  - 캘린더 등록·실제 착용은 강한 선호, LIKE는 약한 선호로 분리
  - DISLIKE와 사유는 부정 신호로 보존
  - 단순 추천 노출은 선호가 아닌 반복 회피 자료로만 사용
  - 저장 코디는 약한 선호, 상품 클릭은 중립 참고 신호로 분리
- [x] 회원 전용 추천 코디 멱등 저장·해제 API와 카드 `is_saved` 응답
- [x] 회원 전용 상품 클릭 이벤트 API와 동일 상품 5분 중복 제거

  - 현재 저장 중인 최신 100건의 코디·아이템·스타일·색상·핏·슬롯 집계

  - 최신 100건과 앱 복귀 시 기록한 근사 체류 시간을 참고 정보로 제공
  - 체류 시간이 길어도 클릭만으로 선호로 판정하지 않음
  - 같은 카드의 저장 또는 LIKE가 있을 때만 선호 보강 근거를 표시
  - 채팅 문장의 긍정 표현 추출은 별도 후속 작업으로 분리

## 3.11 실험형 가설 스키마와 LLM 생성 구현

### 구조화 출력

요청당 가설 2개를 생성한다.

```json
{
  "hypotheses": [
    {
      "change_axes": ["bottom_silhouette"],
      "preserve_axes": ["top_style", "color_family"],
      "reason_code": "RECENT_SILHOUETTE_REPETITION"
    }
  ]
}
```

### 허용값 계약

변경·유지 축은 다음 값만 허용한다.

- 슬롯 스타일: `top_style`, `bottom_style`, `outer_style`, `footwear_style`
- 스타일 관계: `style_mix`
- 실루엣: `top_silhouette`, `bottom_silhouette`, `outer_silhouette`
- 색상 관계: `color_family`, `color_contrast`
- 조합 관계: `proportion`, `layering`, `material_mix`, `pattern_density`
- 미사용 탐색: `underused_item_slot` (변경 축 전용)

사유 코드는 다음 값만 허용한다.

- `RECENT_SLOT_REPETITION`
- `RECENT_SILHOUETTE_REPETITION`
- `RECENT_STYLE_REPETITION`
- `RECENT_COLOR_REPETITION`
- `RECENT_COMBINATION_REPETITION`
- `CALENDAR_ITEM_UNDERUSE`
- `STRONG_PREFERENCE_ANCHOR`
- `SAME_COLOR_MATERIAL_VARIATION`

가설은 변경 축 1~2개와 유지 축 1~3개로 구성한다. 같은 축을 동시에 변경·유지할 수 없으며, 요청 결과는 변경·유지 축 조합이 서로 다른 가설 정확히 2개여야 한다.

### 입력

- 현재 사용자 요청
- 날씨와 TPO
- 선호·기피 태그
- 최근 추천 10회 요약
- 캘린더 착용 통계
- 저장·LIKE 신호

### 금지 사항

- 상품·옷장 아이템 ID 생성
- 최종 코디 선택
- 존재하지 않는 아이템 속성 생성
- 하드 조건 우회
- 고정된 레트로·강한 색 키워드 반복

### 진행 상태

- [x] ID 없는 변경·유지 축 enum과 허용값 정의
- [x] 최근 추천·착용·강한 선호 근거로 제한한 reason code enum 정의
- [x] 변경 축 1~2개·유지 축 1~3개 및 상호 배타 검증
- [x] 요청당 정확히 2개 가설과 축 조합 중복 검증
- [x] 알 수 없는 필드·아이템 ID·Validator 우회 필드 거부
- [x] 최근 추천·캘린더·피드백을 ID 없는 빈도 요약으로 변환
- [x] 기존 메인 OpenAI 어댑터를 통한 가설 전용 구조화 출력 호출
- [x] 가설 전용 프롬프트에서 아이템 선택·속성 생성·하드 조건 우회 금지
- [x] 개별 가설 필터링
  - LLM 전송 스키마와 최종 허용값 스키마를 분리해 두 후보를 독립 검증
  - 구조 오류·동일 축 중복·컨텍스트 근거 없는 reason code만 개별 제거
  - 유효한 LLM 가설은 유지하고 부족한 개수만 규칙 fallback으로 보충
  - 부분 보충은 `HYBRID`, 전부 거부는 `RULE_FALLBACK`으로 실행 출처 기록
  - 거부 개수와 안전한 거부 코드만 가설 스냅샷에 저장
- [x] 반복 슬롯 → 반복 실루엣 → 캘린더 미착용 → 소재/비율 순서의 결정적 fallback
- [x] 제공자 실패·API 설정 누락 시 추천 예외 대신 규칙 가설 2개 반환
- [x] LLM/fallback 출처와 안전한 오류 코드의 실행 스냅샷 구조 제공
- [x] 구조화 가설을 검색어·후보 점수·최근 이력 거리로 변환하는 실험형 공통 전략 연결

### 검증과 fallback

- 허용 축과 reason code만 통과시킨다.
- 중복 가설을 제거한다.
- 모두 실패하면 최근 반복 슬롯 변경 규칙을 사용한다.
- 다음 순서로 fallback을 검토한다.
  1. 최근 반복된 주요 슬롯 변경
  2. 최근 반복된 실루엣 변경
  3. 최근 캘린더 기록에 없던 아이템 활용
  4. 동일 색상군 안에서 소재·비율 변경

### 완료 조건

- LLM 성공 시 유효한 가설 2개 이하가 생성된다.
- LLM 실패 시 추천 전체가 실패하지 않는다.
- 실험형이 최근 추천과 다른 탐색 요청을 생성한다.

## 3.12 추천 파이프라인을 후보 생성과 최종 저장으로 분리

### 변경 이유

현재 파이프라인은 유효한 후보를 찾으면 즉시 저장한다. 이 구조에서는 스타일리스트 간 중복을 확인하고 후순위 후보로 교체하기 어렵다.

### 목표 흐름

```text
후보 검색
→ 코디 조합
→ Validator 검증
→ 페르소나별 유효 Top-K 반환
→ 스타일리스트 간 중복 검사
→ 최종 1개 선택
→ DB 저장
```

### 호환성

- 기본 모드는 기존처럼 최대 3개의 검증된 조합을 저장한다.
- 스타일리스트 모드는 전략별 Top-K 중 최종 1개만 저장한다.
- Retriever·Composer·Validator의 기존 구현을 최대한 재사용한다.

### 진행 상태

- [x] `generate_candidates()`가 Retriever → Composer → Validator를 실행하고 DB 저장 전 유효 후보 묶음을 반환
- [x] 후보 묶음에 ChatRun·세션·identity·응답 모드·추천 모드 범위를 고정해 다른 실행 후보의 저장 차단
- [x] `persist_candidates()`가 외부에서 재정렬·선택한 후보만 트랜잭션으로 저장하고 커밋 후 렌더 작업 예약
- [x] 기본 모드는 같은 골든 템플릿의 검증 후보 최대 3개, 스타일리스트 모드는 개별 실행당 1개만 저장
- [x] 기존 `execute()`를 생성·저장 호환 진입점으로 유지해 첫 성공 템플릿을 저장하던 기본 추천 동작 보존
- [x] 후보 생성 무저장·선택 저장·다른 템플릿 혼합 차단·기본 모드 회귀·스타일리스트 단건 저장 테스트 추가
- [x] 스타일리스트 전략별 후보 생성·재정렬 연결
- [x] 스타일리스트 간 중복 검사와 최종 후보 선택 경계 연결

### 완료 조건

- 후보 생성 단계가 DB 저장 없이 유효 후보를 반환한다.
- 오케스트레이터가 중복 검사 후 선택 후보만 저장할 수 있는 명시적 경계를 제공한다.
- 기존 기본 추천 테스트가 통과한다.

## 3.13 스타일리스트별 독립 검색·조합 실행

### 목표

공통 후보 하나를 세 전략이 나눠 고르는 방식이 아니라 검색 질의와 조합 점수를 전략별로 분기한다.

### 스타일리스트별 실행

- 전략별 검색 질의 구성
- GoldenOutfit 후보 검색
- 아이템 후보 검색
- 코디 조합 생성
- 공통 Validator 실행
- 전략별 재정렬
- 유효 Top-K 반환

공통 프로필·날씨·옷장·추천 이력 조회는 다시 실행하지 않는다.

### 진행 상태

- [x] 전략 검색 계획의 검색어·소프트 선호/기피·후보 수를 GoldenOutfit Retriever 입력에 반영
- [x] 페르소나마다 GoldenOutfit 검색 → 아이템 검색 → 코디 조합 → 공통 Validator를 별도로 실행
- [x] 검증 후보의 실제 아이템 ID는 내부 이력 비교에만 사용하고 전략에는 ordinal·태그·정규화 지표만 전달
- [x] 공통 컨텍스트에서 최근 태그·반복 슬롯·미착용 카테고리·날씨·행동 요약을 한 번 변환해 재사용
- [x] 미니멀·실용형 전략을 실제 검증 후보 재정렬에 연결
- [x] 실험형 가설을 동적 검색어와 새로움·이력 거리·미착용 활용·교차 스타일 점수로 연결
- [x] `ChatRunPersona.strategy_snapshot`에서 실행 전략을 복원해 접수 후 설정 변경의 영향 차단
- [x] 페르소나별 유효 Top-3와 점수·근거 코드를 DB 저장 전 결과로 반환
- [x] 세 전략의 검색어·후보 수가 다르고 공통 TPO·계절·예산 Validator 조건은 같은지 통합 테스트
- [x] 병렬 실행·상태 전이·부분 실패와 중복 검사 후 최종 저장 연결

### 완료 조건

- 같은 사용자 요청에서도 전략별 검색 요청이 구분된다.
- 각 전략이 공통 하드 조건을 동일하게 적용한다.

## 3.14 병렬 실행과 부분 실패 처리

### 병렬 실행

- 공통 컨텍스트와 사용자 발화 분석은 한 번만 실행한다.
- 선택된 스타일리스트 추천을 최대 3개까지 병렬 실행한다.
- 작업마다 독립적인 파이프라인·DB 연결 경계를 사용한다.
- 전체 목표 응답시간은 최대 20초로 둔다.

### 상태 처리

- 스타일리스트 한 명 이상 성공: 전체 실행 성공
- 일부 실패: 성공 결과와 실패 정보를 함께 저장
- 모두 실패: 전체 실행 실패
- 공통 컨텍스트 실패: 전체 실행 실패
- 설명 생성 실패: 추천 성공 + 템플릿 설명

완료 카드부터 실시간 표시하는 것은 필수가 아니므로 프론트 폴링 호환성을 우선한다.

### 진행 상태

- [x] 공통 전략 컨텍스트를 한 번 생성하고 선택된 스타일리스트를 최대 3개 스레드에서 병렬 실행
- [x] 작업마다 새 `StylistRecommendationPipeline`과 스레드별 Django DB 연결 사용
- [x] 기본 묶음 제한 시간을 20초로 두고 시간 초과 작업만 `STYLIST_PERSONA_TIMEOUT`으로 실패 처리
- [x] 각 실행을 `PENDING → RUNNING → SUCCEEDED/FAILED`로 독립 전이하고 지연시간·안전한 오류 코드/메시지 저장
- [x] 한 스타일리스트의 후보 생성 또는 최종 저장 예외가 다른 스타일리스트 실행을 취소하지 않도록 격리
- [x] 성공한 Top-K만 스타일리스트 간 중복 검사 후 `RecommendationResult`로 개별 저장
- [x] 중복 검사·전략 실행 계획·실험형 가설 스냅샷과 최종 reason code를 저장 경계에 연결
- [x] 한 명 이상 성공하면 성공·실패 결과를 함께 반환하고, 모두 실패하면 상태 확정 후 전체 실패 예외 반환
- [x] 공통 컨텍스트 실패 시 작업을 시작하지 않고 모든 스타일리스트 상태를 실패로 확정
- [x] `ChatOrchestrator`의 STYLIST 응답 생성·부분 성공·전체 `ChatRun` 종료 연결

### 완료 조건

- 한 스타일리스트 예외가 다른 실행을 취소하지 않는다.
- `ChatRunPersona` 상태와 오류가 정확히 저장된다.

## 3.15 스타일리스트 간 중복 검사

### 선택 순서

```text
minimal → experimental → practical
```

### 중복 기준

- 전체 아이템 ID 동일: 완전 중복
- 상의·하의·아우터·신발 중 3개 이상 동일: 주요 중복
- 사용자가 특정 아이템을 고정: 해당 슬롯 중복 허용

### 중복 처리

- 후순위 유효 후보를 검토한다.
- 대체 후보가 하드 조건을 위반하면 사용하지 않는다.
- 품질이 크게 낮아지면 억지로 다양화하지 않는다.
- 후보 부족 시 중복을 허용하고 이유를 기록한다.

### 진행 상태

- [x] 입력 순서와 관계없이 `minimal → experimental → practical` 고정 순서로 선택
- [x] 출처 유형·컬렉션·원본 ID 전체 집합이 같으면 완전 중복으로 판정
- [x] 상의·하의·아우터·신발 중 같은 슬롯의 동일 아이템이 3개 이상이면 주요 중복으로 판정
- [x] 사용자 고정 슬롯은 완전·주요 중복 비교 대상에서 제외할 수 있는 명시적 입력 제공
- [x] 선순위 결과와 겹치지 않는 후순위 Validator 통과 후보를 Top-3 안에서 탐색
- [x] 기본 허용 점수 하락폭 5점 이내에서만 중복 후보를 후순위 후보로 교체
- [x] 품질 하락·후보 소진·모든 후순위 후보 중복 시 기존 후보를 유지하고 구분된 reason code 반환
- [x] 선택 reason code를 `validated_reason_codes`에 합치고 아이템 ID 없는 중복 판단 스냅샷 제공
- [x] 다른 ChatRun·세션·사용자 후보 및 Validator 미통과 후보의 중복 검사 차단
- [x] 병렬 실행 성공 결과 수집과 중복 검사 후 스타일리스트별 최종 DB 저장 연결

### 완료 조건

- 중복 후보 교체와 허용 사유가 테스트로 검증된다.
- 다양성이 하드 조건과 추천 품질보다 우선하지 않는다.

## 3.16 말투 LLM 제공자 어댑터 구현

### 공통 인터페이스

추천 엔진이 확정한 결과를 짧은 페르소나 문장으로 변환한다.

### 환경설정

```text
PERSONA_LLM_PROVIDER=openai|gemini
PERSONA_LLM_MODEL=...
```

이 설정은 서버 운영용이며 사용자에게 제공자를 선택하게 하지 않는다.

### 입력 제한

- 스타일리스트 ID
- 확정된 코디 ID
- 구성 아이템 이름·슬롯
- 검증된 reason code
- Voice Profile

전체 대화와 전체 옷장은 전달하지 않는다.

### 구현 순서

1. 기존 OpenAI 클라이언트를 이용한 어댑터
2. 동일 계약의 Gemini 어댑터

## 3.18 실패 재시도와 `다른 추천` API

### 실패한 스타일리스트 재시도

- 실패한 스타일리스트 한 명만 다시 실행한다.
- 원본 메시지와 실행 스냅샷을 사용한다.
- 이미 성공한 다른 스타일리스트 결과는 변경하지 않는다.
- 재시도 횟수와 오류 이력을 저장한다.

#### 구현 완료 내용

- [x] 회원 전용 `POST /api/v1/chat/runs/{run_id}/personas/{persona_id}/retry/` 추가
- [x] `FAILED`인 대상 행만 `PENDING`으로 전환하고 성공한 형제 결과 유지

- 지정한 스타일리스트만 새 추천을 실행한다.
- 현재 카드와 최근 추천 10회를 제외 기준으로 사용한다.
- 완전 중복과 주요 중복을 피한다.
- 새 결과는 과거 결과를 덮어쓰지 않고 별도 이력으로 저장한다.

#### 구현 완료 내용

- [x] 회원 전용 `POST /api/v1/chat/runs/{run_id}/personas/{persona_id}/alternative/` 추가
- [x] 대상 스타일리스트만 별도 Redis 작업으로 실행하고 형제 결과 유지

- [x] 완전 중복과 주요 슬롯 3개 이상 중복 후보 제외
- [x] 중복되지 않은 유효 Top-3가 없으면 기존 카드를 유지하고 개별 실패 기록

- [x] Swagger 경로·회원 권한·응답·오류 계약 추가

### 완료 조건

- 재시도와 다른 추천의 목적과 상태가 구분된다.
- 다른 스타일리스트 결과가 다시 실행되지 않는다.

## 3.19 이미지 생성 정책 변경

### 현재 코드와 충돌

기존 추천 파이프라인은 응답 모드를 구분하지 않고 결과 저장 후 `render_jobs.schedule_result`로 검증된 카드들의 이미지 생성을 자동 예약했다.

### 변경 내용

- 기본 추천(`DEFAULT`)은 기존처럼 추천 저장 직후 자동 렌더 예약을 유지한다.
- 스타일리스트 모드(`STYLIST`)는 최초 추천·실패 재시도·`다른 추천` 모두 저장 직후 자동 렌더 예약을 하지 않는다.
- 사용자가 선택한 카드에 대해서만 기존 렌더 접수 API를 호출한다.
- 동일 카드·동일 조합 요청은 캐시와 멱등 처리를 재사용한다.
- 이미지 실패와 추천 실패를 분리한다.
- 이미지 작업만 재시도할 수 있게 한다.

선택 카드 렌더 접수에는 기존 `POST /api/v1/recommendations/{result_id}/cards/{card_id}/render/` API를 사용한다.

### 완료 조건

- 기본 추천 결과는 저장 커밋 후 기존과 동일하게 이미지 작업을 자동 예약한다.
- 추천 결과 저장만으로 스타일리스트 카드 이미지 작업이 생성되지 않는다.
- 카드 선택 API 호출 후 해당 카드 한 장의 작업만 생성된다.

## 3.22 백엔드 실제 작동 확인

자동 테스트 후 가능한 실행 환경에서 다음 흐름을 확인한다.

```text
회원 로그인
→ 채팅방 생성
→ 스타일리스트 목록 조회
→ 미니멀·실험형 선택
→ STYLIST 모드 활성화
→ 메시지 전송
→ ChatRun 완료 대기
→ 스타일리스트 결과 2개 확인
→ 부분 실패 상태 확인
→ 다른 추천 실행
→ 카드 1개 선택
→ 선택 카드 이미지 작업만 생성
```

외부 서비스 의존성을 구분한다.

- PostgreSQL
- Redis와 채팅 worker
- Qdrant
- 텍스트 임베딩 서비스
- OpenAI 또는 Gemini
- S3와 이미지 생성 worker

외부 서비스가 없어도 자동 테스트와 mock으로 검증할 수 있는 영역을 먼저 통과시킨다.

### 백엔드 완료 조건

- 마이그레이션 정상 적용
- 관련 단위·통합 테스트 통과
- 기본 추천 회귀 없음
- 스타일리스트 1·2·3명 실행 가능
- 부분 실패·재추천 가능
- 선택 카드만 이미지 생성
- API 응답이 프론트 연동 가능한 형태로 확정

- 공통 조건 충족 표시
- 접힌 상세 근거
- `다른 추천`
- 실패한 스타일리스트 재시도
- 이미지 생성 상태

전체 카드 완료 전 부분 표시가 필수는 아니므로 기존 run 폴링 완료 후 한 번에 표시해도 된다.

---

## 3.26 카드 선택 즉시 이미지 생성 연결

사용자가 카드를 선택하면 해당 카드의 기존 렌더 접수 API를 호출한다.

- 선택하지 않은 카드는 생성하지 않는다.
- 생성 중 상태를 표시한다.
- 성공하면 생성 이미지로 갱신한다.
- 실패해도 아이템 카드와 추천 설명은 유지한다.
- 이미지 작업만 다시 시도할 수 있다.

## 5. 구현 중 반드시 지킬 경계

- 스타일리스트 3명을 별도 AI 에이전트나 별도 서버로 만들지 않는다.
- 스타일리스트 간 토론과 반박을 추가하지 않는다.
- 기존 Retriever·Composer·Validator를 버리고 새 추천 시스템을 만들지 않는다.
- 공통 후보 하나에 말투만 다르게 붙이지 않는다.
- 실험형을 고정 유행 키워드로 정의하지 않는다.
- 말투 LLM이 코디·아이템·검증 근거를 변경하게 하지 않는다.
- 일부 스타일리스트 실패를 전체 실패로 처리하지 않는다.
- 추천됨·좋아요·저장·클릭·착용을 동일한 신호로 취급하지 않는다.
- 캘린더와 옷장 아이템이 연결되지 않은 경우 아이템 착용을 추측하지 않는다.
- 모든 추천 카드의 이미지를 자동 생성하지 않는다.
- 스타일리스트 모드를 위해 기존 추천 모드 불변 정책을 깨지 않는다.
- 게스트에게 회원 선택값 저장 구조를 억지로 적용하지 않는다.
- 현재 후순위인 체형 강조·보완 목표 기능을 핵심 구현 중 함께 확장하지 않는다.
- 사용자 승인 없이 Confluence나 범위 밖 문서를 수정하지 않는다.

## 6. 현재 코드에서 확인된 주요 사실

- 현재 브랜치는 `feature/chat-main-integration`이다.
- 기존 `ChatSession.mode`는 `WARDROBE_BASED/NEW_ITEM`이며 변경이 금지돼 있다.
- 모드 변경은 기존에 파생 세션 생성으로 처리한다.
- 기존 `PersonaProfile`은 단일 활성 페르소나를 전제로 한다.
- `ChatContextService`는 기본 프로필·옷장 버전·날씨·대화 컨텍스트를 구성하고 Redis 캐시를 사용한다.
- 기존 메인 LLM은 OpenAI Responses API 구조화 출력을 사용한다.
- 기존 추천 파이프라인은 GoldenOutfitRetriever, ItemCandidateRetriever, Composer, Validator를 호출한다.
- `RecommendationResult`는 `ChatRun`과 일대다 관계이며, 기본 결과는 실행당 1개,
  스타일리스트 결과는 `ChatRunPersona`당 1개로 제한한다.
- 현재 기본 추천은 결과 하나에 최대 3개의 `OutfitComposition`을 저장한다.
- 기본 추천은 저장 후 `render_jobs.schedule_result`로 이미지 작업을 자동 예약하고,
  스타일리스트 추천은 사용자가 선택한 카드만 기존 렌더 접수 API로 예약한다.
- 추천 카드 단일 렌더 접수 API와 이미지 작업 SSE는 이미 존재한다.
- 캘린더는 `CalendarEntry`와 `WardrobeItem`을 명시적 N:N 관계로 연결한다.
- 캘린더 상태는 이미지 처리 상태이며 별도 `PLANNED/WORN` 값은 없지만 제품 정책상 캘린더 등록을 실제 착용으로 간주한다.
- 사용자 추구미는 `preferred/avoided` JSON으로 분리 저장된다.
- 추천 카드 `LIKE/DISLIKE` 피드백 모델과 API가 존재한다.
- 백엔드에는 채팅 run SSE가 있지만 모바일은 JWT·React Native 제약 때문에 run 상태 폴링을 사용한다.
- 모바일의 기존 추천 카드 로딩은 AI 메시지 metadata의 단일 `recommendation_result_id`를 기준으로 한다.

이 사실과 다른 코드가 발견되면 새 코드가 기준이며, 차이를 문서와 사용자에게 보고한 뒤 구현 방향을 조정한다.
